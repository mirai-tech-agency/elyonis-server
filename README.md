# elyonis-license

License activation server for Elyonis. Express + Postgres, deployed on
Render; the database is the Neon project `elyonis-license` (eu-central-1,
database `elyonis`, branch `main` = production). Custom domain `app.elyonis.fr`.

## API

All routes return JSON.

| Method | Path                              | Auth          | Body                              |
| ------ | --------------------------------- | ------------- | --------------------------------- |
| POST   | `/api/license/activate`           | none          | `{key, machineId}`                |
| POST   | `/api/license/verify`             | none          | `{key, machineId, token}`         |
| POST   | `/api/license/deactivate`         | none          | `{key, machineId, token}`         |
| GET    | `/api/admin/keys`                 | Bearer ADMIN  | `?limit=100&offset=0&status=&type=&pack=&q=` |
| POST   | `/api/admin/keys`                 | Bearer ADMIN  | `{type, durationDays?, pack?, notes?}` |
| POST   | `/api/admin/keys/:key/revoke`     | Bearer ADMIN  |                                   |
| POST   | `/api/admin/keys/:key/reset`      | Bearer ADMIN  |                                   |
| GET    | `/api/admin/stats`                | Bearer ADMIN  |                                   |
| GET    | `/api/health`                     | none          |                                   |

`GET /api/admin/keys` filters (all optional, omitting them returns everything
as before): `status` is `pool|activated|revoked|expired`, `type` is
`perpetual|subscription|trial`, `pack` is `basic|premium|pro`, `q` matches the
key (dash- and case-insensitive) or the notes field. The response carries
`{ok, rows, total, limit, offset}` — `total` counts the whole filtered set, not
the returned page.

`GET /api/admin/stats` powers the admin dashboard (`elyonis-dashboard`):
aggregate key counts, account counts, a 30-day created/activated series, and
the last 15 audit events. Note `status` has no `expired` value in the schema —
expiry is derived from `expires_at` at read time, so an `activated` key can
also be expired. Hence `accounts.total` (ever activated) vs `accounts.live`
(activated and not expired).

Public endpoints are rate-limited (5 activates / 15 min / IP; 30 verifies / min / IP).

## Local dev

```bash
cp .env.example .env
# generate strong secrets:
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
# paste into HMAC_SECRET and ADMIN_TOKEN, and set DATABASE_URL to a Neon
# dev branch (Neon console → elyonis-license → Branches → create from main).
# The schema is created on first start. Then:
npm install
node scripts/generate-keys.js 10        # seed the DB with 10 test keys
node --env-file=.env src/server.js      # http://localhost:3000
```

## Deploy on Render

One-shot setup using the Blueprint (`render.yaml`).

1. **Push the repo to GitHub** (private repo is fine).
2. **render.com → New → Blueprint** → connect the GitHub repo. Render reads
   `render.yaml`, creates the web service and offers to deploy.
3. **Set secrets** in the new service's "Environment" tab:
   - `DATABASE_URL` — Neon pooled connection string for `main`, with
     `sslmode=verify-full`
   - `HMAC_SECRET` — `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`
   - `ADMIN_TOKEN` — same generator
   - leave `PORT` as Render configured it
4. **Manual deploy** if Render didn't auto-trigger.
5. **Smoke test** the autogenerated URL (e.g. `https://elyonis-license-XXXX.onrender.com/api/health`).

### Custom domain (`app.elyonis.fr`)

1. In Render → service → **Settings → Custom Domains → Add Custom Domain** →
   enter `app.elyonis.fr`.
2. Render shows a `CNAME` target like `XXXX.onrender.com` and an ALIAS / ANAME
   record for the apex case (we're a subdomain so use CNAME).
3. At your DNS registrar for `elyonis.fr` add:
   ```
   Type   Name   Value                      TTL
   CNAME  app    XXXX.onrender.com.         300
   ```
4. Wait ~5 minutes; Render verifies the record and issues a Let's Encrypt cert.
5. The licensing API is then reachable at `https://app.elyonis.fr/api/health`.

### First batch of keys (on production)

`generate-keys.js` writes wherever `DATABASE_URL` points, so it can run from
any machine with the production connection string (or from the Render shell):

```bash
# --pack defaults to basic; a Premium batch must say so (see Pricing model).
DATABASE_URL='<neon main>' node scripts/generate-keys.js 100 perpetual --pack=basic   > batch-basic-001.csv
DATABASE_URL='<neon main>' node scripts/generate-keys.js 100 perpetual --pack=premium > batch-premium-001.csv
```

## Integration with the Elyonis website

The Elyonis website (mirai-tech.fr / elyonis.fr) owns the Stripe checkout
flow. After a successful payment, the website calls our admin endpoint to
mint a key, then emails it to the customer.

### Pricing model (per Christopher / client)

Two independent axes. `type` is the **billing duration**, `pack` is the **feature
set** — any pack can be sold on any type.

| Audience      | Plan                | `type`         | `durationDays` |
| ------------- | ------------------- | -------------- | -------------- |
| B2C (particulier) | Monthly, no commitment | `subscription` | 30             |
| B2B (pro / AGEFIPH)  | Annual                | `subscription` | 365            |
| Lifetime / one-shot  | Perpetual             | `perpetual`    | (omit)         |

| `pack`    | Sold at launch | Features                                                       |
| --------- | -------------- | -------------------------------------------------------------- |
| `basic`   | yes            | Low-vision suite: zoom, filters, pointer, read-aloud, voice **commands** |
| `premium` | yes            | Basique **+ voice dictation** (typing by voice)                  |
| `pro`     | no (reserved)  | Treated as Premium by the client until it has its own features   |

The client enforces this: `elyonis.exe` reads `pack` out of the signed
activation token and closes **Voix → Dictée vocale** on `basic`, replacing the
switch with a link to the clavtek.fr quote form. Everything else stays open —
voice *commands* share the same recognition engine but belong to Basique, so
never gate the mic on the pack.

> **`POST /api/admin/keys` defaults `pack` to `basic`** (entry-level), while the
> DB column defaults to `premium` (grandfathering rows created before packs
> existed). So any caller that omits the field now mints a licence **without
> dictation** — the website's Stripe flow must send `pack` explicitly for every
> Premium sale. Keys minted before this shipped are unaffected: they carry
> `premium` from the column default.

For subscription plans the website re-issues a key extension on each
successful renewal (call POST `/api/admin/keys` again? no -- prefer to
bump the existing key's `expires_at` via a future endpoint, then have the
client `/verify` pick up the new value). v1.0 ships with the simpler
"each payment = fresh key" model; we'll add `/api/admin/keys/:key/extend`
in v1.1 when Stripe recurring webhooks land.

### Website → license server call

```bash
# After Stripe checkout success, the website server does:
curl -X POST https://app.elyonis.fr/api/admin/keys \
    -H "Authorization: Bearer $ADMIN_TOKEN" \
    -H "Content-Type: application/json" \
    -d '{
        "type": "subscription",
        "durationDays": 30,
        "pack": "premium",
        "notes": "customer@example.com / Stripe cs_test_..."
    }'

# Response (HTTP 201):
{
    "ok": true,
    "key": "XGVJX-9YY5S-NBVBB-WFP8D-FHEJG",
    "type": "subscription",
    "pack": "premium",
    "expiresAt": 1782983007
}
```

The website then sends the `key` to `customer@example.com` (Resend /
Postmark / Mailgun) along with a download link to elyonis.exe.

## Operations

### Admin queries via curl

```bash
ADMIN=...your token...
curl -H "Authorization: Bearer $ADMIN" https://app.elyonis.fr/api/admin/keys | jq

# Revoke a stolen key:
curl -X POST -H "Authorization: Bearer $ADMIN" \
    https://app.elyonis.fr/api/admin/keys/XXXXX-XXXXX-XXXXX-XXXXX-XXXXX/revoke

# Force-reset (licensee lost their old PC and can't /deactivate):
curl -X POST -H "Authorization: Bearer $ADMIN" \
    https://app.elyonis.fr/api/admin/keys/XXXXX-XXXXX-XXXXX-XXXXX-XXXXX/reset
```

### Backups

Neon keeps point-in-time history (restore window = the project's history
retention) and supports snapshots. For an off-site copy:

```bash
pg_dump "$DATABASE_URL" -Fc -f elyonis-$(date +%F).dump
```

## Client integration

The Elyonis client (`src/license/`) hardcodes:

```cpp
constexpr const wchar_t* LICENSE_BASE_URL = L"https://app.elyonis.fr";
constexpr const char*    LICENSE_HMAC_PUBKEY = "<base64 of HMAC_SECRET>";
```

The signed token payload is
`{key, machineId, type, pack, expiresAt, issuedAt, v}`. `pack` is the client's
only source of truth for feature gating (there is no separate entitlements
call), and it is re-issued on every `/verify` — so an upgrade Basique →
Premium in the DB reaches the client at its next heartbeat, without
re-activation. Old tokens have no `pack` field; the client reads that as
`premium`, matching the column default.

`HMAC_SECRET` is a SHARED secret -- both server (to sign) and client (to
verify offline). Treat it like a code-signing key: it ends up in every
shipped binary, so don't reuse it for anything else, and rotate it if a
binary leaks (next release renders old tokens invalid; licensees re-activate
silently via `/api/license/verify`).

## Schema versioning

The DB has a `schema_meta.version = '2'` row. Future migrations bump that
value and ship matching SQL. If you change the schema in a backward-
incompatible way, make the migration also bump the version so an old server
binary fails fast against a new DB.
